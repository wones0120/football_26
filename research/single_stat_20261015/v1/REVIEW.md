# Single Stat implementation and validation

Implemented a separate **Single Stat** workspace and `/api/single-stat` contract for touchdowns, total yards and passing yards. Imports preserve the entire native CSV and exact Game Set. Identity resolves native DraftKings IDs only; unresolved rows stay visible and enter the existing queue with an ingest record. The optimizer selects exactly three distinct canonical players from at least two teams, maximizing the requested measured stat. No salary cap, position constraint, opponent maximum, Classic/Showdown projection conversion or export-header guess is introduced.

All reports are research: there is no actual native Single Stat pool/template among the available identified uploads. Live use needs that exact pool, source Game Set/status/scoring-period evidence and, for upload CSV, a verified native template. The app exposes the specific blockers. No account login, contest entry or purchase occurred. Existing live API/defaults/lineups were not changed.

Projection audit: 464,823 raw weekly rows use `nflreadpy`; 24,988 DraftKings aliases exist. Passing/rushing/receiving yards and rushing/receiving TD are observed fields. Exact rare TD subtype coverage is not established by aggregate return/defense/recovery column names, so those requested categories remain unknown. Baselines average the last three distinct observed games before both the source cutoff and requested week, retain raw/ingest lineage and do not claim trained heads or calibrated intervals. Explicit partial-TD and measured-subset research settings preserve unknowns and exclusions rather than filling zeros.

Provider-confirmed exact scope, disabled games, current/early-start locks, original disabled-game locks and scoring-period closure are enforced. Pending/unknown decisions block generation. The long-tail postponement/cancellation/suspension cases require sourced provider decisions; the app does not invent discretion or refunds. Actual-result accounting uses all seven TD subtypes, excludes passing TD, preserves missing categories, explicitly records disabled-game decisions and requires official-stat/scoring-period/suspension attestations. It saves separate evidence and never overwrites forecasts.

The supplied detailed rules are preserved as [user_supplied_rules.txt](user_supplied_rules.txt). The current official [DraftKings overview](https://support.draftkings.com/dk/en-us/game-style-single-stat?id=kb_article_view&sysparm_article=KB0010273), checked 2026-10-15, confirms three athletes and no salary cap. It does not independently verify the entire supplied NFL-specific long-tail text; records disclose this distinction.

## Validation

- **21 new Single Stat tests passed**, covering scoring isolation, all rare TD categories, missing values, identity/scope, legal rosters, disabled/early locks/provider decisions, chronology, immutable round trips, partial/subset research opt-ins, API import/read/optimize/actual contracts, idempotent ingest/queue and actual accounting.
- **18 existing DraftKings export tests passed**. In the earlier combined single-lineup/export run, 95 passed and two unrelated pre-existing single-lineup export tests failed: their mocked string CSV reaches `evaluation_record.record_export` and `hashlib.sha256(content)` requires bytes. Single Stat code is absent from those stacks; that shared module was untouched.
- **21 existing UI workspace-context/lineup-control tests passed**, preserving Classic/Showdown persisted controls and scope behavior.
- `npm --prefix ui run build` passed TypeScript and Vite. Existing bundle-size warning remains.
- Chrome rendered the actual app on isolated localhost UI `:5187` and fixture API `:8017`, with a temporary SQLite database. The native import → readiness → generate/save flow was exercised for all variants: synthetic totals **180 yards**, **90 passing yards**, **6.3 touchdowns**. App reload and library reopen preserved the same total-yards report hash and roster. Source-attested synthetic actual input with all seven TD types and `passing_tds=99` produced **21 TD**, excluding passing TD. Synthetic names/IDs and Game Set are clearly labeled; this is not live contest validation. Final tests further tighten native actual chronology and use `FIXTURE_ACTUALS` for synthetic result records.
